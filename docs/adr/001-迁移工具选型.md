# ADR 001：数据库迁移工具选型

- **状态**：已接受
- **日期**：2026-10-14
- **决策者**：项目所有者
- **相关规则**：`AGENTS.md` §2.1（技术栈）、§2.2（引入新依赖的流程）、§1.1（禁止手改数据库）、§6（ADR 格式）

## 背景

M2 起接入 MySQL 8，需要一个**版本化迁移**工具：把建表/改表写成有序文件、记录已应用到哪一版、
支持重复执行且可回滚。手写 `CREATE TABLE` 或直接改库都不可接受（`AGENTS.md §1.1` 明确禁止手改数据库）。

约束条件：

- 只用 **MySQL 8**，不需要多数据库支持
- 迁移文件要进 Git、能参与 Code Review
- 部署要简单：**迁移文件最好随二进制走**，避免"代码是新版、SQL 文件是旧版"的错配
- 不引入大而全的框架（`AGENTS.md §2.3`）

## 选项

### A. `pressly/goose` —— 选中

- 最新 v3.29.0（约 2026-09），活跃维护
- **库模式是一等公民**：`goose.Up(db, dir)` + `goose.SetBaseFS(embed.FS)` → 迁移文件编译进二进制
- 同时提供 CLI；支持 SQL 迁移与 **Go 迁移**（需要数据回填时有用）
- MySQL 场景有实质改进：`goose_db_version.tstamp` 由 `TIMESTAMP` 改为 `DATETIME`（修掉 2038 上限）、
  新增基于表的 MySQL Locker
- 依赖较轻（按需 import 驱动）
- 要求 **Go ≥ 1.26**（本项目 go.mod 声明 1.27.2，满足）

### B. `golang-migrate/migrate`

- 最新 v4.20.1，同样活跃（近期有安全修复与启动性能修复）
- CLI 最成熟、支持的数据库种类最多（含各类云托管）
- 库模式可用但更绕：要注册驱动、用 `mysql.WithInstance` 包一层，`embed.FS` 需自己接 `source/iofs`
- 依赖更重（为多数据库场景准备）
- 已知痛点：失败后进入 dirty 状态，需要手工 `force <version>` 修复

### C. 自己写迁移脚本 —— 不选

违背 `AGENTS.md §2.3`（自研轮子）：版本表、并发锁、回滚都要自己实现，收益为零。

## 决定

选 **A：`pressly/goose`**。理由按权重排序：

1. **`embed.FS` + 库模式**最贴合我们的部署形态：迁移 SQL 随二进制发布，部署少一步，
   也杜绝了"二进制与 SQL 文件版本不一致"这类难查的问题
2. **依赖更轻**：只用 MySQL，不为几十种数据库买单
3. **MySQL 被认真对待**：2038 修复与表锁 locker 说明维护者在乎 MySQL 用户

## 代价与约束（必须知道）

1. **MySQL 的 DDL 不支持事务**：迁移中途失败会留下"半应用"的表结构，而版本表不会前进。
   应对：DDL 迁移拆小、尽量幂等（`IF NOT EXISTS`），失败后人工确认再修。
   ⚠️ 这是 MySQL 的固有限制，**换 B 也一样**——不是选型带来的问题。
2. **多一个依赖**：需按 `§2.2` 记录引入理由，本 ADR 即为记录。
3. **Go 版本下限被抬高到 1.26**：本项目 1.27.2 满足；将来若需降级 Go，要重新评估。
4. **放弃 golang-migrate 的数据库广度**：若将来接云托管数据库（如 Spanner），可能需要重新选型。

## 后续动作

- [ ] `internal/config` 增加 `database` 段（**密码只从环境变量读**，不进配置文件）
- [ ] 接入 goose：用 `embed.FS` 加载 `migrations/`（需要一个同层 `.go` 文件声明 `//go:embed`）
- [ ] `migrations/0001_init.sql`：表结构由项目所有者设计（`AGENTS.md §3.1`）
- [ ] 迁移的执行入口：独立 `cmd/migrate`，还是 `apid` 启动时自动迁移？（后者要评估多副本并发迁移的风险）
